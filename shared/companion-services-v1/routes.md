# Routes and version/compatibility rules

`operations.json` is the machine-readable inventory. Every operation maps to a method, exact path template, capability, grant class and object/vault scope. An `aliasOf` is one wire route with one staging/receipt authority, not a second implementation. `atFreeze=contractOnly` means a fixture implements the DTO while the production route is **not yet implemented**; a production `/v1/services` must report it unavailable until its handler, policy and conformance tests exist. `unsupported` has no wire route and cannot be inferred from its domain's service-level status. `legacy=true` denotes an already-opened route whose historical pairing/grant behavior is preserved; its listed grant describes the future service classification, not an authorization change to legacy clients.

New routes are under `/v1/services/**` to avoid collision with the strict Content V1 router. `GET /v1/services` itself requires the existing paired bearer but no new grant. A production handler never accepts query credentials. Durable new writes use a JSON body with `opId`. The ephemeral editing POST/PUT advice has no durable opId/outbox: POST returns an inert server token, PUT changes only that live token (ADR-0005). `PUT /v1/services/ingest/jobs/{jobId}/chunks` carries raw bytes, decimal `X-Chunk-Offset`, lowercase-hex `X-Chunk-SHA256`, bounded `Content-Length`, and no JSON wrapper. The server acknowledges only durable contiguous bytes; an exact duplicate chunk at an already committed offset is accepted, otherwise offset/hash conflicts fail. A status read or completion replay is scoped to the same Desktop instance and device that created the job, and rechecks its target grant/vault scope.

The seven knowledge operations added in `2026-09-30.1` use only the currently active registered Vault. `knowledge.createUnique` references the existing Content Mutation and Note DTOs, preserves the exact prepared body/route/opId/noteId, and returns the final collision-safe path in the durable receipt. A retry never changes an old prepared Content route to the new route, nor converts empty expectedRevision to null. Editing GET excludes the requesting device; POST `{vaultId}` reserves an inert 15-second server token, PUT uses `{vaultId,sessionId,generation,editing}` with safe positive generation. PUT cannot allocate or revive expired/released tokens (410), stale generations do not extend expiry, and release/expiry reclaim the 512 live-token budget. Advice failure never blocks actual content saves.

Directories are a live lexical inventory of safe existing relative paths (root `""` first), not directory writes or a durable cursor. `afterPath=` explicitly skips root. Relations use existing index resolution and Catalog bindings intersected with actual Markdown attachment links. Material relation entries require catalog read; reverse `knowledge.materialReferences` requires catalog read AND current-Vault read, not either scope alone. Relation cursors bind device/instance/Vault/permission plus complete filtered snapshot; changed scope/snapshot returns410, invalid offset400. Pages default100, range1..100; paths/targets1024 UTF-8 bytes. No grant, inactive-Vault writer, guessed identity or second relation database is added.

`SafeSource.pageUrl` and `siteOrigin` require the mandatory `safe-web-url` semantic format in `schema.json`, aligned with the existing #169 catalog validator: HTTP(S), no URL userinfo, direct media path, sensitive query key or sensitive key in a twice-decoded fragment. Ordinary work-identifying query parameters and SPA fragments such as `/#/work/42` or `#slide-3` remain intact. `siteOrigin` is an origin only. `pageKind=work-page` requires a `pageUrl`; `capture-page` identifies a collection/listing page. A missing `pageKind` is interpreted conservatively as `capture-page` on ingest, never promoted to work-page. Detail preserves the Catalog's persisted kind. An origin-only input remains capture-page, not an inferred work page. Reject an unsafe source on new ingest; never log or echo it. This is a validation rule, not a URL-fetching facility.

For `IngestBegin.kind` `text`, `url`, or `clipboard`, `text` is required and nonempty. It is the complete user-submitted UTF-8 payload, `sizeBytes` is its UTF-8 byte count and `sha256` hashes those exact bytes; no binary chunks follow. `url` requires `text` to pass `safe-web-url` and is stored as submitted content, **never fetched** by Desktop. Clipboard means caller-supplied text, not host clipboard access; binary clipboard items use `kind=image` or `file` with chunks. For `image`, `video`, and `file`, `text` must be absent and bytes arrive only through the chunk route. A zero-byte payload is invalid for all kinds.

New versions do **not** add fields to old `/v1/capabilities`, `/v1/assets/{id}`, `/v1/vaults`, `/v1/notes*`, or old `/v1/events` messages. `materials.detailV1` returns a new `MaterialDetail` that may include already persisted safe source provenance. `knowledge.vaults` returns a new registered-vault descriptor without switching the active Desktop editor. A non-active vault may be read-only; an unavailable write owner is reported per operation, not hidden by the service summary.

The new catalog carries `bundleRevision`, Desktop instance ID, current gateway generation, permission revision, limits, and per-operation `state`. A client may cache it by instance+generation+permission revision for display, then must refresh after reconnect or `servicesChanged`; server-side request checks remain authoritative. `implemented` does not imply all objects are writable. `notGranted` means a missing explicit class or scope. `temporarilyUnavailable` means an implemented handler cannot currently reach its domain authority. `unsupported` means no safe product authority exists. A client treats absent or unknown operations as unsupported.

For retry, preserve the same `opId`, canonical payload, target and device. The receipt is durable across reconnection and gateway generation change within the same Desktop instance. Mobile must not let a late response from an old generation acknowledge a newer local draft; that local rule does **not** cause the server to repeat a committed write. `OP_ID_REUSED` is a permanent conflict. `RECEIPT_EXPIRED` never executes a destructive mutation again. `expectedRevision` is required for metadata, move and record removal. Existing desired-state Content V1 writes remain unchanged.

New `materials.changes` and `knowledge.registeredChanges` cursors are opaque, monotonic within their domain/scope and carry a snapshot high-water mark. A 410 `CURSOR_TOO_OLD` triggers a clean projection resnapshot only. Legacy `knowledge.changes` at `/v1/sync/changes` remains its existing numeric `after` / `{changes,cursor,hasMore}` contract; it is never silently converted to the new envelope. The typed WSS hint stream contains cursor identifiers, not content bodies; disconnect or missed hints require durable catch-up. Existing foundation `/v1/events` continues heartbeat semantics.

New change cursors encode a device/instance/domain/vault-or-catalog/permission-revision binding opaquely. An initial absent `after` or `m:0`/`k:0` requests a fresh projection; all returned cursors use the scoped opaque form. A hint cursor is a **high-water wake-up target**, not the client's next `after`: the client continues from its last durably applied cursor until it reaches or exceeds the hint, and never skips directly to the hint. Hints are rendered per authenticated device with the same scoped cursor encoding; a stale-scope hint is discarded on permission revision change.

`GET /v1/services/search` returns an immutable per-query result snapshot with a 10-minute lease only when more pages remain. Complete one-page and empty results return `nextCursor:null` without occupying a snapshot slot. Its opaque cursor is bound to Desktop instance, device, query, domains and permission revision; a changed scope, unknown/expired/reclaimed cursor or mismatched query returns 410 rather than continuing against a shifted live result set. A final page (`nextCursor:null`) retires its snapshot before the response; if that response is lost, repeating its cursor returns 410 and the client restarts the search. A new no-cursor request for the same live query reuses its immutable first page. A different paginated query may reclaim this device's oldest snapshot when needed, never another device's; a reclaimed cursor returns 410. At most four active snapshots or 4 MiB per device and 32 or 32 MiB globally are retained, and a request that cannot fit within those hard caps returns 429. A query exceeding 5000 visible hits returns 400 `INPUT_INVALID` rather than a partial cursor. Search results never expose a vault outside the effective device scope.

`POST /v1/services/presentation/open` is a typed, local-main-window handoff, not a remote command. A successful renderer ACK after synchronous navigation returns `state:"accepted"`. If the main window claimed the short-lived offer but its ACK was lost, the one-time operation returns and replays `state:"handoffStarted"`: handoff began, but display completion is **not confirmed**. The client must not retry the same `opId` expecting another navigation. An unclaimed or explicitly rejected offer returns 409 `PRESENTATION_BUSY`; an explicitly rejected opId is retired (same-op retry 410) because partial local navigation cannot be disproved. Stop and grant/device revoke retire old offers and remove remote authority independently of a renderer ACK; a stale claim/ACK cannot revive them.

Resource bodies continue to use domain-owned authenticated routes with `ETag`, single-byte `Range`, 206/304/416, bounded buffers and disconnect/revocation cancellation. No descriptor includes host absolute paths or credential-bearing URLs. Unknown optional response fields may be ignored; unknown enum/state values fail closed. A higher service major version is unsupported; a new minor/revision must preserve known fields and semantics or publish a documented breaking major. A Desktop lacking `/v1/services` may be used only through known old Content V1 routes after read-only capability discovery, never through a mutating probe.
