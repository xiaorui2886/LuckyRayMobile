# ADR-0001 — Companion Services V1

Status: contract-first, production adapters follow in the same #172 program.
Frozen parent: `446c982a4d04dd454f62ec4292759a33ee784e67` / tree `a6d609bdf01a58c1a57d1f9e7840281f45a90b83`.

## Decision and authority

This bundle sits above the existing Companion v1 pinned-TLS, pairing, bearer, device revocation and listener generation. It does not change their routes or wire objects. Existing Content V1 `/v1/capabilities`, `/v1/assets*`, `/v1/vaults`, `/v1/notes*`, `/v1/sync/changes` and `/v1/events` retain their exact request/response/error behavior. In particular, the strict Content V1 schemas never acquire new fields. New fields and writes live only on the explicit routes in `operations.json`.

`GET /v1/services` is authenticated and device-specific. It reports each operation separately as `implemented`, `notGranted`, `temporarilyUnavailable`, or `unsupported`, plus the effective grant class and permitted scope. The operation map is normative: a service-level `available` or `granted` flag is a UI summary, never authorization. The server rechecks effective device grant, scope, object existence, and revocation on every request, stream chunk and commit. A cached catalog is not a credential. Existing paired devices retain old route behavior but receive no new `content.write`, `ingest.write`, `desktop.open`, or all-vault authority merely by being paired. An explicit Desktop Settings grant is required for new operations. No Mobile grant mutation exists.

The only grant classes are `content.read`, `content.write`, `ingest.write`, `desktop.open`, `lsh.remote`. Scopes are the current Desktop material catalog, a named registered Knowledge vault, or a typed Desktop presentation target. No arbitrary path, command, URL fetch, database query, IPC/Tauri method, account secret or DSH chat/run authority is exposed. URL/text/clipboard ingest means content explicitly supplied in the request, never host clipboard access or arbitrary URL fetching. Source fields are read only when already persisted and safe; CDN links are never upgraded into supposed work-page URLs.

## Persistence and retry boundary

Every new write has a caller-generated immutable `opId` and canonical JSON payload. The server binds the receipt key to Desktop instance, device, operation, object/vault scope and payload digest, **not** to the short-lived gateway generation. Same key+payload returns the stored receipt after a lost response, including after process restart; same key+different payload returns `OP_ID_REUSED`. A different device or Desktop instance cannot read or replay another device's receipt. The server writes an intent before crossing a domain mutation and resolves uncertain outcomes by inspecting the domain postcondition; it never blindly repeats a destructive write. Receipt expiry returns an explicit error, never re-executes a destructive op. Connection generation is carried in response identity so Mobile rejects late old-generation acknowledgements; it does not invalidate a lawful same-instance retry.

Metadata, move and removal require `expectedRevision`. Old Content V1 desired-state favorite/tag/folder routes are unchanged. A successful material mutation and its change event commit in the same original database transaction where possible. Local Desktop and remote writes both feed durable domain change cursors. A 410 `CURSOR_TOO_OLD` re-snapshots only a clean Mobile projection; it never clears drafts or outbox. The cursor is scoped to instance, domain, vault/catalog and permission revision. WSS is a wake-up hint only.

Material import and generic ingest are **one** target-scoped job flow. Staging is app-private; chunk offsets/hash and total size are checked before commit. The task is owned by one instance+device+target. Revocation aborts ongoing reads/commit; cancel removes only task-owned staging. A completion receipt is durable and replay-safe. Knowledge note attachments keep their existing Content V1 route, but the new ingest adapter reuses its domain publication policy. No second database or material/knowledge authority is introduced.

### Frozen retention and transaction rules

Full successful write receipts are kept for at least **180 days** after completion. After that, the compact instance+device+operation+opId+target+payload-digest tombstone is retained for the life of the Desktop instance database; matching retries return `RECEIPT_EXPIRED` and never execute the write again, differing payloads return `OP_ID_REUSED`. A missing tombstone after profile/database replacement represents a **new Desktop instance ID**, which Mobile must not silently treat as the old target. Failed validation never reserves an opId. Committed receipts do not depend on listener generation. New destructive mutations cannot be admitted if their intent/tombstone cannot be durably recorded.

Material and Knowledge change entries, including removal tombstones, are retained for at least **30 days**. Pruning records an explicit durable per-domain/per-vault cursor floor; an older cursor returns 410 `CURSOR_TOO_OLD`. A snapshot cursor is bound to Desktop instance, permission revision, domain and vault/catalog; scope/revocation changes invalidate it. Search snapshot pages have a 10-minute lease and are bound to query+device+permission revision; expired/mismatched cursors return 410, never silently skip a live result. The fixture uses deterministic logical state instead of wall-clock sleeps.

An incomplete upload expires after **24 hours of inactivity** and may be cancelled sooner. At most two concurrent jobs and 128 MiB of staged bytes per device are admitted; each job is at most 64 MiB with 256 KiB chunks. Expiry/cancel removes only the private staging object named by that job. Its opId tombstone persists, so a late complete cannot create a new record. Completed upload receipts obey the 180-day/instance-life rule above. Staging and receipts live in the existing backend database plus a private app-data staging directory, not in the user-selected destination.

The write boundary is: authorize and validate; atomically reserve `(instance,device,operation,opId,target,digest)` as `pending` in the owning database; perform the domain mutation with its own revision guard and change-journal entry in the same domain transaction where available; atomically finalize receipt and its cursor. For Knowledge filesystem-backed operations and ingest publication where SQLite and file rename cannot be one transaction, persist intent before file action, use an app-private staged file and atomic rename/domain op marker, then reconcile on restart by inspecting that stable marker and target revision. An uncertain commit returns `SERVICE_UNAVAILABLE` while pending; it is **never blindly retried**, especially for delete/import. A response is sent only after receipt durability. Revocation and target scope are rechecked immediately before the domain commit. Legacy Content V1 already owns its note op/upload intent path and remains unchanged.

## Compatibility and availability

Clients must ignore unknown optional response fields and unknown enum values conservatively; they must not execute unknown operations. Major version mismatch disables that service. Additive minor changes require a new bundle revision and digest, never an in-place semantic edit. When `/v1/services` is absent on an old Desktop, a client may use only the documented old Content V1 read/desired-state routes after `GET /v1/capabilities`; no side-effecting POST probe. `implemented` describes a production handler, `notGranted` a denied effective grant/scope, `temporarilyUnavailable` a real but currently unavailable runtime/source, and `unsupported` an absent safe product authority. Fixture support never makes production `implemented` true by itself.

The reference fixture is synthetic and loopback-only. It cannot be built into the production Gateway and accepts no real profile, pairing secret or user data. Its success and failure cases are contract tests, not LAN/TLS/real-device evidence.
