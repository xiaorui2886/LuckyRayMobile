# Companion content V1 — preview and durable note synchronization

Status: implementation decision, 2026-09-12. Authority: Desktop Issue #120;
Mobile Issue #26 is its execution index. This is an additive content contract,
not a replacement for the tested Companion pairing/session/TLS contract.

## Ownership and compatibility

The authoritative content bundle is this Desktop `protocol/companion-v1/content-v1`
directory. Mobile consumes a byte-identical vendored copy with source revision
and digest recorded; shared fixtures and both consumers' tests must agree before
advertising the capability. Mobile's earlier `shared/protocol-v1` remains the
legacy field/error vocabulary, not a second independently editable wire authority.

An authenticated capabilities response announces `contentVersion: 1` and only
implemented domain capabilities: material preview, note read/write, note changes,
and note attachment publication. Existing hello/pair/session/events continue to
work for old clients. Missing capabilities disable only the corresponding desktop
content UI, with an upgrade explanation. Capture, AI, LSH and material writes are
not enabled by this work. The existing sync coordinator invokes a content-only
native operation, never the legacy capture/AI sync implementation.

## Identity and authority

Desktop KnowledgeService and files remain the note content authority. Its existing
backend SQLite stores the minimal stable-ID mapping, change journal and operation
receipts; it is not another editable note store. Note identity is `(desktop
instance, vault registration, opaque note ID)`. Paths and content hashes are not
business IDs. Mapping keeps IDs for existing paths and explicit service moves;
filesystem identity/observed rename evidence reconciles external renames. Ambiguous
delete/create observations are preserved as distinct changes, never guessed from
equal content. Revisions cover content and path metadata, so rename races conflict.

The first implementation exposes the currently authorized real Vault. A request
binds its exact vault/target identity and must fail on a switch/re-registration;
requesting another vault never activates or switches the desktop editor. The wire
shape includes vault identity so registered-vault browsing can extend this without
changing entity keys. Material IDs retain the catalog's existing identity and
storage-mode semantics. No desktop absolute path is exposed as a resource API.

## Narrow domain routes

All content routes require the existing pinned HTTPS Bearer credential. Query keys
are allowlisted for pagination, filtering and cursors; credentials are never URL
parameters. Foundation query rejection stays intact. Content routes include:

- `GET /v1/capabilities`, `/v1/vaults`.
- `GET /v1/assets` (page/limit/query/kind/folder/tag), `/v1/assets/:id`,
  `/v1/assets/:id/thumbnail`, `/v1/assets/:id/file`.
- `GET /v1/notes` (vault, keyset snapshot page, directory/query),
  `GET /v1/notes/:id` (vault), `POST /v1/notes`,
  `PATCH /v1/notes/:id`, `DELETE /v1/notes/:id`.
- `GET /v1/sync/changes` (vault/after/limit), authenticated attachment resolution
  and opaque resource reads scoped to a note; a staged/chunked attachment publish
  operation scoped to a note and client operation ID.

Schemas/types/fixtures specify the exact final shapes alongside implementation.
No arbitrary command, database table, filesystem path or generic upload endpoint
is provided. Note responses preserve original Markdown and return separately
resolved attachment descriptors; the mobile render layer does not rewrite the
saved note into local temporary paths. Rendering does not execute raw HTML/scripts
or follow `file:`/unapproved schemes.

## Atomicity, retries and conflicts

Each mutation binds `opId`, vault identity, note ID, immutable submitted payload and
`expectedRevision`. An existing opId with different payload is rejected. A durable
intent is committed before invoking the Knowledge service. Intent stages and the
observed resulting file revision recover a crash after file commit but before
receipt/change commit. New IDs and destination paths are fixed before create;
retries cannot generate another note. Success receipts are durable and replayed.
Content publication and note submission are separate recoverable operations.

Remote mutations share Knowledge's mutation/source guards and optimistic revision
checks. The active desktop dirty-draft state vetoes remote mutation with a retryable
busy result; in-flight desktop edits still retain their existing revision conflict
and dirty-editor protection. Remote changes must never replace an unsaved renderer
draft. Local save debounce remains 1600ms. Rename/content updates use a recoverable
staged intent through existing move/write APIs, including attachment rewrites.
Delete saves recoverable operation content before invoking the existing deletion
service, then journals a tombstone; an offline edit against deletion conflicts.

Mobile extends its existing versioned SQLite note cache with a durable draft
generation, last server document and immutable in-flight operation. Every edit is
saved locally; an acknowledgement confirms only its captured generation. Later
input remains dirty and gets a later operation based on the acknowledged revision.
A lost response retries the same opId and payload. Dirty local data survives remote
tombstones, cache reset, disconnect and re-pairing in its original namespace.

409 `REVISION_CONFLICT` preserves both server document and local draft. The UI offers
view both, use desktop, or retain local as a new copy. A conflict copy uses one
durable create opId so retries cannot multiply copies. No last-writer-wins or
speculative automatic merge. Renaming an offline draft does not alter its entity
ID. Revoked/source-changed requests cannot acknowledge a new session's draft.

## Change recovery and bounded I/O

WSS is a wake-up hint, not the source of truth. Monotonic durable changes include
tombstones. Startup and watcher reconciliation repair missed filesystem changes;
content request handling reuses the indexed inventory instead of scanning the
whole vault for each keystroke or thumbnail. Initial snapshot pages use stable-ID
keyset ordering and a captured high-water mark; newer revisions are obtained by
replaying changes after that mark. Cursor/data application commits in one Mobile
SQLite transaction. An expired cursor returns 410 `CURSOR_TOO_OLD`; resnapshot
replaces only the clean desktop projection and never clears drafts or local data.
Bounded batches schedule continuation instead of silently truncating at one page.

Resources resolve through existing catalog/Knowledge authorization. Reads provide
MIME, length, ETag/version and single byte-range semantics (206/416); open files are
streamed in bounded chunks and stop on disconnect/revocation. Mobile on-demand
downloads stream to private staging with length/version checks and atomic cache
publication; video playback must use a valid local/range-capable media source,
not a whole-video byte array crossing IPC. Cached data is instance/resource/version
scoped. Offline missing resources show a cache/offline state, not a fake preview.

New mobile note attachments stay in a private draft staging area. A bounded chunk
upload is resumable by operation ID/offset and checked length/digest; completion
uses Desktop's existing attachment publication strategy and returns a real
reference. A draft depends on that receipt before note submission. Interrupted
publication resumes; unreferenced completed files are retained for deferred review,
never automatically deleting another note's original asset.

## Delivery and rollback

Both repositories use the task's stacked Draft PRs and existing working directories.
Preserve current desktop generated dirty files, mobile app data, pairing and signing
identity. Migrations are additive/versioned and tested against the existing schema.
Back up the installed APK and record its certificate/hash before `adb install -r`.
USB is for installation/debugging only; acceptance uses real LAN without adb reverse.
Old APK rollback cannot consume new pending drafts: preserve the newer data and use
an explicit compatible forward recovery/export rather than resetting the database.
No merge, self-ALLOW or release is part of implementation completion.
